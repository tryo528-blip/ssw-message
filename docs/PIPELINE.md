# 처리 파이프라인 (v1)

> 사무실에 도착한 암호문이 ERP가 쓸 파일이 되기까지.
> 핵심은 **검증과 보정을 분리**하는 것이다.

---

## 1. 왜 2단계인가

현장 요구: **다시 찍어올 수 없는 사진이 있다.**

따라서 폰은 "잘 도착했다"가 확정되기 전에 로컬 데이터를 지우면 안 됩니다.
그런데 문서 보정은 장당 수 초가 걸립니다. 폰이 그걸 기다리면 현장에서 서 있는
시간이 늘어납니다.

**폰이 확인해야 하는 것은 "사진이 온전히 도착했는가"지 "보정이 끝났는가"가 아닙니다.**
그래서 둘을 쪼갭니다.

| | 1단계 · 검증 | 2단계 · 보정 |
|---|---|---|
| 하는 일 | 복호화 → 해시 대조 → 정규화본 저장 | 문서 영역 감지 → 원근 보정 → 판독성 향상 |
| 소요 | 수백 ms | 장당 수 초 |
| 폰 | **기다림** (완료 시 로컬 삭제) | 무관 (이미 떠남) |
| 실패하면 | 폰이 데이터를 계속 보유 → 재전송 가능 | 정규화본이 남아 있음 → 손실 없음 |

2단계가 실패해도 **데이터가 사라지지 않는 것**이 이 구조의 핵심입니다.

---

## 2. 1단계 · 검증

```
inbox/enc/ 에 파일 도착 (inotify로 즉시 감지)
  → key_id 확인
  → 복호화
  → 입력 검사 (아래 2.1)
  → 정규화 (아래 2.2)
  → ready/photo/<날짜>/ 에 정규화본 저장
  → status/<submissionId>.json 기록   ← 폰이 조회할 완료 신호
  → 암호문을 _processed/ 로 이동
```

여기까지 끝나면 **"안전하게 도착했다"가 확정**됩니다.
폰은 이 시점에 로컬 암호문을 지웁니다.

### 2.1 입력 검사

> 이 절은 선행 프로젝트 WorkCadenceTransfer 의 사진 정규화 정책 v1 을 따릅니다.
> 그쪽에서 이미 다듬어진 기준이라 그대로 흡수합니다.

| 검사 | 기준 | 위반 시 |
|---|---|---|
| MIME | `image/jpeg` 정확히 일치 | `INVALID_MEDIA` |
| 시그니처 | JPEG SOI + 유효한 frame header | `INVALID_MEDIA` |
| EXIF Orientation | 값이 1~8 (없으면 1로 간주) | `INVALID_MEDIA` |
| 선언 크기 | `files[].bytes` == 실제 바이트 수 | `CONTENT_DIGEST_MISMATCH` |
| 선언 해시 | `files[].sha256` == 실제 SHA-256 | `CONTENT_DIGEST_MISMATCH` |
| 장당 용량 | ≤ 5 MiB | `RESOURCE_LIMIT_EXCEEDED` |
| 전체 용량 | ≤ 25 MiB | `RESOURCE_LIMIT_EXCEEDED` |
| 해상도 | width·height 각 ≤ 4096px, 총 ≤ 12MP | `RESOURCE_LIMIT_EXCEEDED` |
| 구성 | 메모만 / 사진 1~5장 / 메모+사진. 둘 다 비면 거부 | `INVALID_SUBMISSION` |

**한도를 넘으면 자동 축소하지 않고 거부합니다.** 서버가 사용자 모르게 이미지를
바꾸지 않는다는 원칙입니다. 앱이 애초에 2200px로 만들어 보내므로 정상 경로에서는
걸릴 일이 없고, 이 검사는 방어선입니다.

**원본 파일명은 읽지도, 저장하지도, 로그하지도 않습니다.**

### 2.2 정규화

보정과 달리 **실패할 수 없는 결정적 변환**만 합니다. 그래서 1단계에 둡니다.

1. EXIF Orientation을 픽셀에 적용하고 Orientation=1로 고정
2. 모든 메타데이터 제거 (EXIF, GPS, XMP, IPTC, 썸네일, 코멘트, 원본 파일명)
3. sRGB 색공간으로 통일
4. 8-bit RGB로 새 비트맵에 그린 뒤 JPEG quality 90 으로 재인코딩
5. 결과물이 5 MiB를 넘으면 `RESOURCE_LIMIT_EXCEEDED`

> 앱에서 canvas 재인코딩으로 이미 EXIF가 소멸하지만, 서버에서 한 번 더 보장합니다.
> **클라이언트를 신뢰하지 않는 것이 원칙입니다.**

사진은 한 장씩 제한된 메모리에서 처리하고, **평문 임시 파일을 만들지 않습니다.**

### 2.3 재인코딩과 멱등성의 분리

`contentDigest` 는 **전송된(wire) 바이트** 기준으로 계산합니다.
서버가 재인코딩한 저장본의 해시는 digest 계산에 쓰지 않습니다.

따라서 같은 제출을 재전송하면 **저장본이 달라지더라도 같은 digest, 같은 판정**을 받습니다.
저장본의 실제 크기·해시·적용된 Orientation은 메타 JSON에 따로 기록합니다.

## 3. 2단계 · 문서 보정

정규화본을 입력으로 받아 **보정본을 추가로** 만듭니다. 정규화본은 그대로 둡니다.

```
정규화본 읽기
  → 그레이스케일 + 약한 블러 (노이즈 감소)
  → CLAHE 로 지역 대비 향상       ← 문서 경계 검출률을 크게 올림
  → Canny 엣지 + Contour 추출
  → 사각형 후보 4점 탐색
  → 문서로 판단되면 원근 변환 (perspective transform)
  → 배경 추정 후 제거 → 백색화 + 글자 대비 강화
  → 약한 샤프닝
  → ready/photo/<날짜>/<recordId>_1_scan.jpg 저장
```

구현: Python + OpenCV. 리눅스 미니PC이므로 `apt` 로 설치합니다.

### 실패를 전제로 설계한다

문서 영역 자동 감지는 **실패합니다.** 배경이 어수선하거나, 종이가 접혔거나,
그림자가 지거나, 문서가 화면 밖으로 잘리면 엉뚱하게 잘라냅니다.

그래서 다음을 강제합니다.

- **정규화본을 항상 보존합니다.** 보정본은 부가물입니다
- 사각형 후보를 못 찾으면 **보정을 시도하지 않고 건너뜁니다.** 억지로 하지 않습니다
- 검출된 사각형이 전체 면적의 20% 미만이거나 종횡비가 비상식적이면 기각합니다
- 보정 실패는 로그에 남기고 알림을 보냅니다. **데이터 손실이 아니므로 에러가 아닙니다**

메타 JSON에 결과를 기록합니다.

```jsonc
"files": [
  {
    "name": "01M07…_1.jpg",              // 정규화본 (항상 존재)
    "scan": "01M07…_1_scan.jpg",         // 보정본 (실패 시 null)
    "scan_status": "ok",                 // "ok" | "skipped" | "failed"
    "scan_reason": null                  // 실패·건너뜀 사유
  }
]
```

ERP는 `scan` 이 있으면 그걸 쓰고, 없으면 정규화본을 씁니다.

## 4. 상태 조회 (폰 ↔ 서버)

폰이 1단계 완료를 확인하는 경로입니다.

```
POST /api/status
본문: { id, device_id, sig }        ← 자기 것만 조회 가능
```

| 응답 | 의미 | 폰의 행동 |
|---|---|---|
| `{ verified: true, verified_at }` | 1단계 완료 | **로컬 삭제** |
| `{ verified: false }` | 아직 처리 중 | 계속 폴링 |
| `{ error: "FAILED", reason }` | 1단계 실패 | 보유 유지 + 재전송 안내 |
| `404` | 도착 기록 없음 | 재전송 |

**Receiver는 개인키 없이 이 API를 제공합니다.** Collector가 써둔
`status/<id>.json` 을 읽어 돌려줄 뿐입니다. 키 분리 원칙이 유지됩니다.

폴링: 1초 간격, 최대 15초. 그 안에 확인되지 않으면 "전달됨 · 확인 대기"로
대기함에 남기고, 앱을 다시 열 때 재확인합니다.

---

## 5. 폰 대기열 정책

**변경: 기존 "6시간 후 자동 폐기" → "확인될 때까지 보관"**

다시 찍을 수 없는 사진이 있으므로 시간 기준 폐기는 위험합니다.

- 확인되지 않은 건은 **암호문 상태로 계속 보관**합니다
- 폰에는 개인키가 없으므로 앱 자신도 열 수 없습니다. 개인정보 위험 없음
- 홈 화면에 미확인 건수를 상시 표시하고, 대기함에서 재전송할 수 있습니다
- 7일이 지나면 경고를 띄우되 **자동으로 지우지 않습니다.** 사용자가 판단합니다
- 재전송은 멱등성(`id`)이 보장하므로 중복 걱정 없이 눌러도 됩니다

## 6. 최종 산출물

```
ready/photo/2026-08-17/
├── 7f3a91c2-….json             # 메타 + 메모 + 파일 목록
├── 7f3a91c2-…_1.jpg            # 정규화본 (항상)
├── 7f3a91c2-…_1_scan.jpg       # 보정본 (성공 시)
├── 7f3a91c2-…_2.jpg
└── 7f3a91c2-…_2_scan.jpg
```

저장 경로에는 **서버가 생성한 `recordId`(UUID)만** 씁니다.
기기가 만든 `submissionId`, 원본 파일명, 기기 모델명은 경로에 쓰지 않습니다.

### ready/ 는 평문입니다 — 그래서 디스크를 암호화합니다

선행 프로젝트는 `ready/` 에도 레코드 키로 암호화해 저장했습니다. 우리는 ERP가 이 폴더를
직접 읽는 구조라 평문이어야 합니다. 그 공백은 **미니PC 전체 디스크 암호화(LUKS)** 로 덮습니다.

- 도난·반출 시 보호됨 (부팅 전 디스크는 읽을 수 없음)
- ERP는 평소처럼 폴더를 읽음 (동작 변경 없음)
- 수집 완료분은 보존기간 후 자동 삭제 (개인정보 사진은 7일 권장)

리눅스 미니PC이므로 설치 시 LUKS를 켜는 것으로 끝납니다. 운영 부담이 없습니다.

## 7. 성능 예상

| 구간 | 예상 | 근거 |
|---|---|---|
| 폰 암호화 (300KB) | ~1ms | 실측 (2026-08-17) |
| 업로드 | 회선 의존 | 바이너리 전송으로 base64 33% 절감 |
| 1단계 검증 (장당) | 100~300ms | 복호화 + 해시 + JPEG 재인코딩 |
| **폰 체감 대기** | **1~2초** | inotify 즉시 감지 + 1초 폴링 |
| 2단계 보정 (장당) | 1~5초 | OpenCV, N100급 CPU |

미니PC 사양 권장: N100급 저전력 CPU, RAM 8GB, SSD 256GB 이상.
보정이 CPU 작업이라 RAM은 4GB보다 8GB를 권합니다.
