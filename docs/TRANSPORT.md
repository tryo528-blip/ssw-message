# 전송 경로 재검토 — 개인정보 제3자 미경유 요건 (v0.2)

> 요건 추가: **사진은 전부 개인정보다. 제3자 서버에 남으면 안 된다.**
> 이 문서가 DESIGN.md 3장의 결론을 대체한다.

---

## 1. 사실 정리 — 무엇이 "남는" 것인가

경로를 고르기 전에 용어를 나눠야 합니다. 셋은 위험도가 전혀 다릅니다.

| 구분 | 의미 | 예 |
|---|---|---|
| **저장(storage)** | 제3자 디스크에 파일로 남음 | Google Drive에 사진 파일이 있음 |
| **경유(transit)** | 제3자 메모리를 평문으로 스쳐감. 저장은 안 됨 | Cloudflare 엣지의 TLS 종단 |
| **메타데이터** | 내용은 모르고 통신 사실만 앎 | DNS 조회, 접속 IP·시각·용량 로그 |

Cloudflare Tunnel은 **저장이 아니라 경유**입니다. POST 본문은 캐시되지 않고 디스크에
쓰이지 않습니다. 그러나 TLS를 엣지에서 종단하므로 평문이 제3자 메모리를 한 번 지납니다.
"남지 않는다"는 맞지만 "거치지 않는다"는 틀립니다.

Google Drive(A안)는 **명백한 저장**입니다. 게다가 서버가 국외라 개인정보 국외이전
이슈까지 얹힙니다. 사내 방침이 엄격하면 이 한 줄로 탈락합니다.

---

## 2. 두 갈래 해법

### 해법 X — 경로에서 제3자를 아예 없앤다

폰 → **사무실 PC** 로 직접 TLS. 중간에 아무도 없습니다.

### 해법 Y — 경로를 믿지 않아도 되게 만든다 (E2E 암호화)

폰에서 **사무실 공개키로 암호화한 뒤** 보냅니다. 중간에 누가 있든 암호문만 봅니다.
복호화 키는 사무실에만 있습니다.

둘은 배타적이지 않습니다. **X + Y가 최상**이고, X가 불가능한 환경이면 Y 단독으로도
"제3자에게 개인정보가 남지 않는다"는 요건을 충족합니다.

---

## 3. 해법 X — 사무실 직접 수신 (제3자 경유 0)

```
폰 ──── TLS(종단간) ────▶ 사무실 PC ──▶ 로컬 디스크 ──▶ ERP 수집
                          (수신 서버 + PWA 서빙 동일 출처)
```

핵심 난관은 **인증서**입니다. `getUserMedia`는 보안 컨텍스트를 요구하는데,
사설 IP에는 정상 인증서를 못 붙입니다. 해결책:

**무료 DDNS + Let's Encrypt**

- 무료 서브도메인 발급 (예: `sswmsg.duckdns.org`) — DuckDNS 등, 비용 0
- 공유기에서 443 포트포워딩 → 사무실 PC
- Let's Encrypt로 정식 인증서 자동 발급·갱신 (Caddy 쓰면 설정 3줄)
- 결과: 폰이 사무실 PC와 **직접** TLS를 맺음. 중간자 없음

제3자로 남는 건 **DNS 사업자(이름→IP 변환만 앎)** 와 **인증서 발급기관(발급 사실만 앎)**
뿐입니다. 둘 다 사진 데이터를 볼 수 없습니다. 개인정보 처리위탁 대상이 아닙니다.

**PWA도 이 서버에서 서빙합니다.** 앱 코드와 수신 엔드포인트가 같은 출처가 되어
제3자 호스팅이 사라집니다 (5장에서 다시 다룸).

### 필요 조건 — 이게 안 되면 X는 불가

| 조건 | 확인 방법 | 안 될 때 |
|---|---|---|
| **공인 IP** | 공유기 WAN IP와 `whatismyip` 결과가 같은지 비교 | 다르면 CGNAT → 통신사에 공인 IP 요청(무료인 경우 많음) 또는 해법 Y |
| **포트포워딩 권한** | 공유기 관리자 접속 가능 여부 | 불가 시 해법 Y |
| **PC 상시 가동** | 24시간 켜둘 수 있는 PC 1대 | 불가 시 해법 Y |

### 장단점

- ✅ 제3자 데이터 경유·저장 0. 요건에 정확히 부합
- ✅ 비용 0. 도메인도 DDNS로 대체
- ✅ 사진이 곧바로 사무실 디스크에 도착 → 수집 지연 없음
- ⚠️ 사무실 PC가 인터넷에 노출됨 → **수신 전용 최소 서비스만** 열고, ERP 본체와 분리
- ⚠️ PC가 꺼지거나 회선이 끊기면 전송 불가 → 폰에 암호화 대기열 필요 (7장)

## 4. 해법 Y — E2E 암호화

경로가 무엇이든 제3자는 암호문만 봅니다. 브라우저 기본 API(Web Crypto)만으로 구현되고
외부 라이브러리가 필요 없습니다.

```
[최초 1회] 사무실에서 키쌍 생성
           공개키 → QR로 각 폰에 배포
           개인키 → 사무실 PC + 오프라인 백업 2벌

[전송할 때마다]
  1) 폰: 임시 키쌍 생성 (ECDH P-256)
  2) 폰: 임시개인키 + 사무실공개키 → 공유비밀 → HKDF-SHA256 → AES-256 키
  3) 폰: AES-256-GCM 으로 사진 암호화 (iv 12B 랜덤, AAD = 전송 id)
  4) 전송: { epk(임시공개키), iv, ciphertext }   ← 임시개인키는 즉시 폐기
  5) 사무실: 개인키로 같은 공유비밀 유도 → 복호화
```

- P-256 ECDH + AES-GCM은 **iOS Safari·Android Chrome 모두 네이티브 지원**합니다
  (X25519는 최신 브라우저만 지원하므로 P-256 선택)
- 전송마다 임시 키쌍을 새로 만들므로 한 건이 뚫려도 다른 건은 안전합니다
- 암호화는 기밀성만 줍니다. **위조 방지는 별도**로 기기 토큰 + HMAC 서명이 필요합니다
- 봉투 메타데이터 중 `id`/`created_at`만 평문으로 두고(파일명·멱등성 처리용),
  `user`·`site`·`body`는 암호화 대상에 포함합니다

### 부수 효과 — 사무실 디스크도 보호됨

해법 X를 쓰더라도 Y를 얹으면, 수집 전까지 사무실 디스크에 놓인 파일도 암호문입니다.
사무실 PC가 랜섬웨어나 내부자 접근에 노출돼도 사진 내용은 보호됩니다.

### 대가 — 키를 잃으면 끝입니다

개인키를 분실하면 **미수집 데이터는 영구 복구 불가**입니다. 이건 버그가 아니라 설계의
본질입니다. 운영 규칙으로 강제해야 합니다.

- 개인키를 USB 2개에 나눠 보관, 최소 1개는 사무실 밖 금고
- 담당자 1인 단독 보관 금지
- 키 교체 절차 문서화 (새 공개키 QR 재배포 → 구 키는 기존 미수집분 복호화용으로 보존)

## 5. 솔직한 한계 — 웹 E2E 암호화의 급소

암호화 코드를 **누가 폰에 배달하는가**의 문제입니다.
앱을 서빙하는 서버가 악의적으로 바뀌면, 암호화를 우회하는 자바스크립트를 내려보내
평문을 빼돌릴 수 있습니다. 웹 기반 E2EE의 고전적 약점이고, 정직하게 말해 이건
암호학으로 못 막습니다.

대응:

- **PWA를 사무실 서버에서 직접 서빙** (해법 X와 결합하면 제3자 호스팅이 사라짐) ← 가장 확실
- 서비스워커로 앱 셸을 고정하고 버전 핀 + 무결성 해시 검증
- 네이티브 앱 + 코드 서명이면 근본적으로 해결되지만 iOS 배포에 연 $99 → 비용 요건과 충돌

**해법 X를 택하면 이 급소가 함께 사라집니다.** X를 우선하는 진짜 이유입니다.

## 6. 최종 비교

| | X: 직접 수신 | X+Y (권장) | Y 단독 (Drive) | 기존 A안 (평문+Drive) |
|---|---|---|---|---|
| 제3자 **저장** | 없음 | 없음 | 암호문만 | **평문 저장** ❌ |
| 제3자 **경유** | 없음 | 없음 | 암호문만 | 평문 |
| 사무실 디스크 유출 시 | 평문 노출 | **보호됨** | 보호됨 | 평문 노출 |
| 앱 코드 공급망 위험 | 없음(자체 서빙) | 없음 | 존재 | 존재 |
| 국외이전 이슈 | 없음 | 없음 | 논란 여지 | **있음** |
| 비용 | 0 | 0 | 0 | 0 |
| 필요 조건 | 공인IP·포트·상시PC | 좌동 + 키관리 | 없음 | 없음 |
| PC 다운 시 | 전송 불가 | 전송 불가 | 전송 가능 | 전송 가능 |

**결론: X + Y 를 기본안으로 한다. 공인 IP나 포트포워딩이 막히면 Y 단독으로 후퇴한다.**
기존 A안(평문 + Drive)은 새 요건에서 **폐기**합니다.

## 7. 가용성 보완 — PC가 꺼져 있을 때

해법 X의 유일한 실질 약점입니다. 사진은 원칙적으로 폰에 남기지 않기로 했지만,
전송 실패 시 무조건 폐기하면 현장에서 사진을 다시 찍어야 합니다.

절충안: **암호화 상태로만 대기열에 넣습니다.**

- 실패한 사진은 **이미 사무실 공개키로 암호화된 상태**로 IndexedDB에 보관
- 폰에서는 누구도(앱 자신도) 복호화 불가 — 개인키가 없으므로
- 최대 6시간 보관 후 자동 폐기, 홈 화면에 대기 건수 상시 표시
- 갤러리가 아닌 앱 전용 샌드박스이므로 "갤러리 저장 금지" 요건은 유지

즉 **평문 사진은 어떤 경우에도 기기에 존재하지 않습니다.** 메모리에서 canvas → 암호화까지
간 뒤에야 저장 가능한 형태가 되고, 그 시점에는 이미 우리도 못 읽습니다.

## 8. CONTRACT 변경 예고 (v2)

암호화 도입으로 봉투 구조가 바뀝니다. 확정 후 `CONTRACT.md`를 v2로 개정합니다.

```jsonc
{
  "schema": "ssw-msg/2",
  "id": "01J5K7P2Q4",                    // 평문 (파일명·멱등성)
  "created_at": "2026-08-17T09:12:40+09:00",  // 평문 (정렬·보존정책)
  "enc": {
    "alg": "ECDH-P256+HKDF-SHA256+AES-256-GCM",
    "key_id": "office-2026-08",          // 키 교체 대비
    "epk": "BEt3...",                    // 임시 공개키 (raw, base64)
    "iv": "9f2c...",                     // 12바이트
    "ct": "…"                            // 암호문: envelope 나머지 + 이미지 전체
  },
  "sig": "hmac-sha256:…"                 // 기기 토큰 기반 위조 방지
}
```

수집기는 복호화 후 기존 v1 구조를 그대로 얻습니다. **ERP 투입 로직은 변경 없음.**

## 9. 착수 전 확인 3가지

X안 가능 여부가 여기서 갈립니다. 셋 다 "예"여야 X로 갑니다.

1. **공인 IP인가?** 공유기 관리페이지의 WAN IP와 `whatismyip.com` 결과 비교 → 같으면 O
2. **공유기 포트포워딩을 설정할 수 있는가?** (관리자 비밀번호 보유)
3. **24시간 켜둘 PC가 있는가?** (기존 ERP 서버와 별도 권장)
